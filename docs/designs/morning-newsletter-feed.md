# Design: Morning Newsletter Feed (today-only, out of the inbox)

Generated by /office-hours on 2026-11-06
Branch: main
Repo: PGoyal-06/newsletter
Status: APPROVED
Mode: Startup

## Problem Statement

Parth subscribes to 12+ newsletters (TLDR family, Half Baked, Idea Browser, The Batch, Codedex, news.network.ai, more). They land in a Gmail inbox with 17,000+ unread emails. The unread count itself is aversive: "seeing such a massive unread emails number (17000+) on the gmail app just doesn't make me wanna open the app altogether." The newsletters are valuable when they reach Parth ("I sometimes find one ... and go through it, read any interesting articles"), but they are trapped behind an inbox Parth avoids.

Reframed: **a calm morning feed that pulls newsletters out from behind an inbox you avoid, showing only today's issues and nothing else.** Read on an iPhone during the morning commute; content must be ready on open.

## Demand Evidence

- n=1. The only confirmed user is the founder. No one else has been named.
- The founder's pain is specific and behavioral: avoids opening the Gmail app because of the badge count; reads newsletters only when one is stumbled upon.
- Market signal is weak for a business: Stoop (newsletter reader) shut down on 31 Oct 2025. Meco PRO ($39.99/yr) already connects directly to Gmail. Readwise Reader ($7.99-8.99/mo), Feedbin ($7/mo) and Kill the Newsletter (free) require forwarding or re-subscribing to a new address. Most-cited reason people quit reader apps: it became "another unread inbox" and they forgot to open it.

## Status Quo

Newsletters pile up unread in the Gmail inbox. No filters, labels or reader apps have been tried. Occasional serendipitous reading when one is found.

## Target User & Narrowest Wedge

- Target user: the founder. A second human with the same symptom (10k+ unread, subscribed to newsletters, reads on a commute) has not been identified yet; finding three is part of the assignment.
- Wedge: an app that shows today's newsletters, on the home screen, no inbox and no count.

## Constraints

- ~$0/month. Free tiers only.
- Full-time intern: must be buildable in 1-2 weekends.
- Knows Next.js, React Native, Expo.
- iPhone, morning commute; possibly patchy signal.
- Never delete anything from Gmail. Gmail is the backup and the archive.
- No AI summaries in v1.

## Premises (agreed)

1. v1 is a personal tool for n=1. "Would others pay?" is unproven; revisit after 2 weeks of own use plus 3 real people found.
2. The core problem is an inbox you avoid, not missing reader features. Any design that reintroduces a count or a backlog fails.
3. Today-only feed: the app shows only recent issues (rolling ~24h), with no unread counts and no archive. Gmail (label + archive, never delete) holds history.
4. Success = opened on at least 8 of the first 10 commute mornings. If not, fix the ritual or the content, not the feature list.

## Key Insight

Every newsletter reader is built as a library (all issues, read/unread state) because it assumes users want to catch up. For an inbox-avoidant reader the backlog is the pain. An expiring feed is both the differentiator and the simpler build: no read state, no storage of history, no counts.

## Approaches Considered

- **A) Apps Script all-in-one (HtmlService UI).** Rejected: 2-4s loads, Google banner, no offline. Recreates friction (premise 2).
- **B) Apps Script backend + Next.js PWA on Vercel.** Chosen.
- **C) Native Expo + own Gmail OAuth client + server worker.** Rejected for v1: $99/yr, server-side token handling with silent-failure risk, built for users who don't exist yet (premise 1).

## Recommended Approach: B

### Why

- Apps Script runs as the account owner with Google-managed OAuth, so there is no OAuth client, no refresh-token storage, and no 7-day Testing-mode expiry. (Verified: Testing-mode refresh tokens expire after 7 days; personal-use apps whose only user is the developer are exempt from verification; Apps Script installable time-driven triggers can read and label Gmail as the owner.)
- A PWA gives a home-screen icon, an instant open from cache, and offline reading at $0, with the UI in Next.js.
- Clean seam: the PWA only knows a JSON contract. The backend can later be swapped (for example for a Gmail API worker if this goes multi-user) without touching the UI.

### Architecture

```
Gmail ──(every 15 min, Apps Script trigger, runs as owner)──┐
  1. find new inbox threads with a List-Unsubscribe header  │
  2. known sender → add label Newsletters/<Category>, archive│
     unknown sender → add label Newsletters/Unsorted, leave in inbox (v1 safety)
  3. rebuild today.json (rolling 24h window) → Drive file   │
                                                            ▼
Apps Script doGet(?key=SECRET) → returns today.json (ContentService, JSON)
                                                            ▼
Next.js PWA (Vercel, static/client-side) → service worker caches shell + last JSON
  → feed (cards + category filter) → reader (sanitized, sandboxed iframe)
```

**Backend (Apps Script, one project):**
- **One 15-minute trigger**, not a separate 5am job. Newsletters arrive at different times (some after 6am), so a single morning build could miss them. Rebuilding every 15 minutes means the snapshot is always current, which removes the question of when the fetch runs. Well inside consumer quotas (90 min/day of trigger runtime).
- **Bounded search, backlog never touched:** each run calls `GmailApp.search('in:inbox newer_than:2d', 0, 100)`. The 17k existing backlog is never scanned or modified. If old newsletters are wanted later, that is a separate, chunked one-off job (out of scope for v1).
- **Per-message processing marker (not a thread label):** Script Property `lastProcessedAt` (epoch ms, one small value). Each run iterates every message in the returned threads and processes only those with `getDate() > lastProcessedAt - 15min overlap`, then sets `lastProcessedAt` to the run start time. Label and archive are idempotent, so the overlap is safe. A new issue that Gmail threads into an older, archived thread moves that thread back into the inbox, so `in:inbox` catches it and the per-message date check processes just the new message.
- **Detection:** `message.getHeader('List-Unsubscribe')` present → newsletter candidate.
- **Category map:** a hand-written object in the script keyed by `List-Id` header first, then sender address, for example `{'<list-id or from>': 'AI'}`. Unmapped senders → `Unsorted`.
- **Unknown-sender safety:** transactional senders (banks, receipts, shipping) also send List-Unsubscribe. In v1 only mapped senders are archived; unmapped ones are labeled `Newsletters/Unsorted` and stay in the inbox. They still appear in the app's feed under "Unsorted" so the founder can add them to the map.
- **Snapshot:** `today.json` = `{ ok: true, generatedAt, items: [{ id, threadId, sender, senderEmail, subject, receivedAt, category, html | null, gmailUrl }] }` for labeled messages in the last 24h, newest first. Written to a single Drive file (CacheService values cap at 100KB and expire within 6h; Script Properties cap at 9KB per value, so neither fits ~1-2MB of HTML).
- **Unsorted items are metadata only:** for `Unsorted` (unmapped) senders, `html` is `null`. Only sender, subject, time and a `gmailUrl` (`https://mail.google.com/mail/u/0/#all/<threadId>`) are included, so bank statements, receipts and shipping notices are never copied into the Drive file, the endpoint or the PWA cache. Full HTML is included only for senders the founder has explicitly mapped to a category.
- **doGet:** constant-time compare of `key` query param against a Script Property secret. Deployed as "Execute as: me, Who has access: Anyone". Optional `?refresh=1` triggers a rebuild for a manual pull-to-refresh.
- **Error contract:** Apps Script web apps always return HTTP 200, so errors travel in the body. Bad key → `{ ok: false, error: "bad_key" }`. The whole handler is wrapped in try/catch, so any caught failure → `{ ok: false, error: "internal" }`. Client rule: **only** `bad_key` sends the user back to setup. `internal`, non-JSON bodies (Google's HTML error page), timeouts and network errors keep the cache and show the stale/offline state.
- **Key rotation:** if the URL+key leaks, generate a new random secret in Script Properties (the old key fails with `bad_key` immediately) and paste the new one into the PWA setup screen. No redeploy needed.
- **Never deletes.** Only label and archive operations.

**Frontend (Next.js PWA on Vercel free tier):**
- Client-side app (static export is enough); `manifest.json` + service worker.
- **First run:** setup screen to paste the doGet URL+key; stored in localStorage of the installed PWA (iOS home-screen apps have their own storage separate from Safari, so key entry happens after Add to Home Screen).
- **Open flow:** load the cached `today.json`, **drop every item whose `receivedAt` is older than 24h by the device clock**, render the rest immediately with "Updated 7:15am", fetch fresh in the background, swap in (applying the same 24h filter). Pull-to-refresh calls `?refresh=1`. This keeps the feed today-only even after skipped days or an offline commute: stale cache never becomes a backlog.
- **Unsorted cards** show sender, subject and time with an "Open in Gmail" action (`gmailUrl`) instead of the in-app reader.
- **Feed:** one card per issue: sender, subject, time, category chip. Category filter chips at the top; last selection remembered. No unread dots, no counts.
- **States:** loading (first run only), empty ("Nothing new today. Everything older is in Gmail under Newsletters."; also shown when every cached item has expired and the refresh failed, together with the stale banner), stale (banner if `generatedAt` > 3h old: "Couldn't refresh since 6:00am", which is the guard against silent failure), offline (show cache, note offline), error (bad key → back to setup).
- **Reader:** sanitize with DOMPurify (strip script/iframe/form/object/embed and on* handlers), drop tracking pixels (imgs ≤2px or with `display:none`), inject `<base target="_blank">`, a CSP meta (`script-src 'none'`), and mobile CSS overrides (`img{max-width:100%;height:auto}`, `table{width:100%!important}`, 17px base font, 16px padding). Render in `<iframe sandbox="allow-popups allow-popups-to-escape-sandbox" srcdoc=…>` with no `allow-scripts` or `allow-same-origin`. Iframe fills the viewport and scrolls internally (auto-height needs same-origin, which the sandbox forbids). Article links open in Safari's in-app sheet, which is unavoidable and fine.
- Remote images still load, so senders can see opens. Accepted for v1.

**Cost:** $0 (Apps Script, Drive, Vercel Hobby).

## Open Questions

1. **Window definition:** rolling 24h vs "since 6pm yesterday". Rolling 24h is the default; check after a week whether skipped days feel guilt-free.
2. **Do TLDR variants share a sender address?** If so, the `List-Id` header must drive categories. Check headers of 3 TLDR issues before writing the map.
3. **Unsorted senders:** how many legitimate newsletters land in Unsorted in week 1, and is editing a JS object to map them tolerable, or does the app need a "set category" action (which requires a write endpoint)?
4. **Payload size:** ~15 issues × 50-150KB HTML ≈ 1-2MB per fetch. Fine on LTE; revisit (list + per-issue fetch) if opening feels slow.
5. **iOS storage eviction:** home-screen PWAs are generally exempt from Safari's 7-day storage purge, but confirm the key survives two weeks.
6. **Web Push (iOS 16.4+ home-screen PWAs):** a 7am "6 issues ready" nudge is the v1.1 candidate if premise 4's metric fails due to forgetting.

## Success Criteria

- Opened on ≥8 of the first 10 commute mornings (log it by hand or with a simple open timestamp).
- Zero important emails wrongly archived in week 1 (check `Newsletters/*` labels once).
- Opens to content in <1s from cache, including offline.
- Stale banner appears within 3h if the trigger breaks (test by disabling the trigger).

## Distribution Plan

Personal web service. Vercel auto-deploys on push to `main` (free Hobby tier). Apps Script is edited in the script editor or pushed via `clasp`. Gotcha: update the existing web-app deployment ("Manage deployments → edit → new version") so the doGet URL stays the same. Install on iPhone via Safari → Share → Add to Home Screen.

- No Apple developer account, no Google Cloud OAuth client.

### R2-1 — feasibility (minor)

**Problem**

> No locking is specified between the `?refresh=1` rebuild inside doGet and the 15-minute trigger run. Two concurrent runs can process the same messages and write the Drive file at the same time. (Carried over from R1-6.)

**Remedy**

> Wrap process-and-rebuild in LockService.getScriptLock() with tryLock. When the lock is held, refresh returns the current snapshot.

### R2-2 — feasibility (minor)

**Problem**

> The quota claim still checks only trigger runtime. Each of the 96 runs/day now iterates every message in up to 100 inbox threads and rebuilds the full 24h snapshot, re-reading HTML and headers. Gmail read-call volume is never estimated. (Carried over from R1-7.)

**Remedy**

> Estimate GmailApp calls per run x 96. Otherwise rebuild only when new messages were processed (or on refresh), or cache HTML per message ID.

### R2-3 — clarity (minor)

**Problem**

> The design does not say where the snapshot takes each item's category from (the Newsletters/<Category> label or a fresh map lookup). The lastProcessedAt marker means an Unsorted message is never reprocessed once its date has passed, so it is also unspecified whether adding a sender to the map re-categorizes or archives today's Unsorted items. List-Id parsing ('Name <id>') is still not defined. (Carried over from R1-9.)

**Remedy**

> State the category source for the snapshot. State whether a map edit affects already-processed Unsorted items (for example, re-evaluate items in the 24h window on each rebuild). State that the map key is the List-Id value inside the angle brackets.

### R2-4 — clarity (minor)

**Problem**

> The query that builds the snapshot ('labeled messages in the last 24h') is still unspecified. The processing search is `in:inbox` only, so it would miss the archived mapped newsletters. The snapshot needs its own query that includes archived mail. (Carried over from R1-10.)

**Remedy**

> Give the snapshot query, for example 'label:Newsletters newer_than:2d', and filter by message date to 24h in code.

### R2-5 — completeness (minor)

**Problem**

> Plain-text-only newsletters from mapped senders still have no defined handling. `html | null` now also signals 'Unsorted, metadata only', so a mapped issue with no HTML part is ambiguous for the client. (Carried over from R1-11.)

**Remedy**

> For mapped senders, fall back to escaped getPlainBody() wrapped in <pre> or paragraphs, so html is null only for Unsorted items.

### R2-6 — consistency (minor)

**Problem**

> Open Question 6's push copy, '6 issues ready', still puts a count back, against premise 2. (Carried over from R1-12.)

**Remedy**

> Reword it without a number, for example 'Today's newsletters are ready'.

### R2-7 — clarity (minor)

**Problem**

> The success metric's 'simple open timestamp' still needs either local-only storage or a write endpoint. Open Question 3 rules out a write endpoint. (Carried over from R1-13.)

**Remedy**

> State that open timestamps go to localStorage and show on a hidden debug screen, or that logging is by hand only.

### R2-8 — completeness (minor)

**Problem**

> The remembered category filter can still hide every item on a day that category has no issues. This looks like a false empty state. (Carried over from R1-14.)

**Remedy**

> Fall back to 'All' when the remembered category has no items today, or show 'Nothing in <Category> today' with the other chips still visible.

### R2-9 — scope (minor)

**Problem**

> Dependencies still list iOS 16.4+ as a v1 requirement. That version matters only for Web Push, which is v1.1. (Carried over from R1-15.)

**Remedy**

> Mark iOS 16.4+ as a v1.1 (Web Push) dependency.

### R2-10 — completeness (minor)

**Problem**

> Metadata-only Unsorted items still expose the subject line through the 'Anyone' endpoint, the Drive file and the PWA cache. Transactional subjects can carry sensitive data: order amounts, tracking numbers, sometimes one-time codes. So 'bank statements, receipts and shipping notices are never copied' holds for bodies only.

**Remedy**

> Either accept and state that Unsorted subjects are exposed, or mask or truncate Unsorted subjects (for example sender plus time only) until the sender is mapped.

### R2-11 — completeness (minor)

**Problem**

> No initial value is given for lastProcessedAt on the first run, when the property is unset. The behavior for a run that throws partway through is also unstated: does it still advance the marker?

**Remedy**

> State the first-run default (for example, now minus 24h) and that lastProcessedAt is written only after the run completes successfully.

### R2-12 — completeness (minor)

**Problem**

> If the trigger is broken for more than 2 days, or more than 100 inbox threads arrive in the window, newsletters that arrived during the gap are never labeled or archived. They stay in the inbox permanently. The feed is not affected because they fall outside 24h.

**Remedy**

> Note this as accepted, or widen the window to cover the gap since lastProcessedAt (capped) on the next run.

### R2-13 — feasibility (minor)

**Problem**

> A `https://mail.google.com/mail/u/0/#all/<threadId>` link opened from an iOS home-screen PWA goes to Safari's mobile Gmail web, not the Gmail app, and the thread deep link may not resolve there. It can also land the founder on the inbox view with its unread count, which is the friction premise 2 is meant to avoid.

**Remedy**

> Verify the link on the iPhone during the build, and document the fallback (for example, a search URL on the subject, or accept landing in Gmail web).

### R2-14 — consistency (minor)

**Problem**

> Architecture diagram step 1 still says 'find new inbox threads with a List-Unsubscribe header'. That does not reflect the new bounded search and per-message lastProcessedAt check.

**Remedy**

> Update step 1 to 'search in:inbox newer_than:2d (max 100); per message newer than lastProcessedAt, check List-Unsubscribe'.
